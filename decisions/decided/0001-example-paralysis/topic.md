# 論点 0001: まひ状態の扱い(記入例)

- **種別: 決定的**(同じ状態 → 同じ合法手。指標で測る要素が無い)
- **状態: 決定済み**
- **反映先: `docs/0001-example-status-condition.md`**(シナリオ S0001_01〜05)

> これは決定済み論点の記入例。書式・番号・承認点の正本は `.claude/rules/decision-rules.md`。
> 新規プロジェクトでは参考にしたら削除する(TEMPLATE.md 手順3)。

## 何を決めるか

状態異常(まず「まひ」)をエンジンがどう扱うか。未対応だと合法手判定が誤る。

## 案

| | 案A:合法手の生成側で落とす | 案B:実行時に非合法手を弾く |
|---|---|---|
| 合法手の定義 | core だけが持つ | core と app で二重管理になる |
| 探索(src/app) | 非合法手が候補に入らない | 木を広げてから弾くので無駄が出る |
| 依存方向 | 崩さない | app 側が合法手の知識を持つ = 崩れる |

## 決定

**案A を採る。** 合法手の生成側(`get_legal_actions`)で落とす。

## 理由

案B は合法手の定義が2箇所に分かれ、片方だけ直したときにもう片方が古い仕様のまま残る。
依存方向(core ← app)の不変条件にも触れる(`.claude/rules/impl-rules.md`「不変条件」)。

## 却下した案

- 案B(実行時に弾く)— 上記のとおり二重管理と依存方向の破壊を招くため。
- 状態異常ごとに個別のフラグを持つ案 — 種類が増えるたびに状態の形が変わり、
  `battle_state` の契約が安定しないため。`status_condition` の1概念にまとめる。

## 決まらなかったこと(次の論点へ)

- まひ以外の状態異常の優先順位・重複時の解決順 → 別論点として `undecided/` に切り出す。
