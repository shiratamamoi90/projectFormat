# 文書のルール(要件定義・基本設計・LLM Wiki としての `docs/`)

> 本文中の例(まひ・ベンチ・`S0001_xx` など)は説明用の架空の題材で、このプロジェクトの仕様ではない
> (読み方は CLAUDE.md 冒頭の注記が正本)。

## どこに何を書くか(置き場の使い分け)

**文書に書くのは、コードを読んでも分からないことだけ。** ファイル分割・関数名・クラス構成・
内部の持ち方(**詳細設計**)は**ソースツリーを見れば分かる**ので、文書に写さない。写すと同じ知識が
2箇所になり、片方だけ直して古いまま残る(@impl-rules.md「共通化」)。

| 置き場 | 持つもの | 理由 |
|---|---|---|
| `docs/requirements/` | **要件定義**:満たすべき振る舞い(機能要件)と制約(非機能要件) | コードからは「何を満たすべきか」が読み取れない(今の実装が正しいかを判定できない) |
| `docs/design/` | **基本設計(外部設計まで)**:構成要素の境界と責務・外部との契約・概念データ・非機能の実現方針・セキュリティ設計 | 部品の外から見える約束は、コードの都合で変えてよいものではない |
| `docs/` の説明ページ | 全体像・一次資料の要約・概念の解説・目録・作業記録 | 規範を読みやすくする地図。規範そのものではない |
| `decisions/` | **なぜそう決めたか**。案の比較・却下した案・理由 | コードには結果しか残らない。理由は消える |
| `src/` `tests/` | **どう作ったか**(詳細設計と実装) | 読めば分かる。文書に写すと二重管理になる |
| `sources/` | **一次資料の原本**(仕様書・議事録・PDF 等)。不変 | 要約や判断の出典。書き換えると根拠が消える |

### 迷ったときの判定(上から順に当てる)

1. **ソースツリーを読めば分かるか** → 分かるなら**書かない**(コードが正本)。
   例:`status_condition.py` に置いた / 関数名が `compute_legal_actions` — すべてコード側。
2. **テスト関数に落とせるか** → 落とせるなら要件定義にシナリオとして書く。
3. **構成要素の境界・責務、外との契約、データの概念か** → 基本設計に書く。
   例:「合法手の定義は対戦エンジンだけが持つ」は基本設計。それをどのファイルに置くかはコード側。
4. **「なぜ」に当たるか** → `decisions/` の論点に書く。コードからは論点番号だけ参照する
   (@impl-rules.md「コメント」)。
5. **一次資料に書いてあることか** → 要約ページ(説明)に出典付きで書く。規範にするかは論点で決める。
6. どれでもないなら、**そもそも書かなくてよい**ことが多い。

> **フォーマット共通の制約は文書に書かない。** 依存方向(core←app)・命名・共通化は
> @impl-rules.md と @architecture.md が正本で、個別プロジェクトで書き直さない。
> 基本設計に書くのは「この制約のもとで、このプロジェクトの部品がどう分担するか」であって、制約そのものではない。

## wiki の構成

`docs/` は **LLM Wiki** として運用する。人間は一次資料を集め、論点を決め、承認する。
LLM は一次資料を取り込み、決まったことを整理し、全体を読みやすく保ち続ける。
**ページの種類はフォルダで決まる**(状態をフォルダで表すのは `decisions/` と同じ考え方)。

```
sources/                 一次資料の原本(不変・既定で git 追跡外)
docs/
├── index.md             目録:全ページを1行要約付きで載せる入口(説明)
├── log.md               作業記録:追記専用の時系列(説明)
├── overview.md          全体像:何を作るか・どこまで決まったか(説明)
├── glossary.md          用語集:ドメイン語彙の正(規範)
├── requirements/        要件定義(規範)
├── design/              基本設計(規範)
├── summaries/           一次資料ごとの要約(説明。出典必須)
└── concepts/            概念・比較・横断の解説(説明)
```

| 種類 | 置き場 | 中身を変える手段 | 整理(意味を変えない) |
|---|---|---|---|
| **規範ページ** | `requirements/` `design/` `glossary.md` | **人間の承認を経た `/decide` だけ** | LLM が自由に行ってよい(下の「wiki の運用」) |
| **説明ページ** | 上記以外 | LLM が `/ingest`・`/tidy` で自由に更新してよい | 同左 |

- **説明ページに規範を書かない。** 「〜しなければならない」と読める内容は規範ページにだけ置き、
  説明ページからはリンクで指す(決まっていないものを決まったように見せない)。
- 一次資料の扱い(取り込み・機密・指示を含みうる点)は @security-rules.md「エージェントの防御」。

## wiki の運用(取り込み・決定・整理・点検・問い合わせ)

**決めるのは人間、整理し続けるのは LLM。** どの操作も最後に `index.md` を更新し、`log.md` に1件追記する
(書式は `log.md` 冒頭。`scripts/validate.sh` が「索引とリンク」「作業記録の書式」で検査する)。

| 操作 | 何をするか | 規範ページ | 実行 |
|---|---|---|---|
| 取り込み(ingest) | 一次資料を読み、要約ページを作り、関連する説明ページ・目録を更新する。規範との食い違いや新しい要件の候補は**論点として開く** | **変えない** | `/ingest` |
| 決定(decide) | 承認された論点を規範ページへ統合する | 論点の範囲だけ変える | `/decide` |
| 整理(tidy) | ページの分割・統合・移動・並べ替え・相互リンク・説明の書き直し・目録と全体像の更新 | **意味を変えずに**移してよい | `/tidy` |
| 点検(lint) | 孤立ページ・切れたリンク・食い違い・古くなった記述・ページの無い概念を探す | 変えない(見つけたら論点か `/tidy` へ) | `/validate`・`/tidy` |
| 問い合わせ(query) | `index.md` から読み、出典付きで答える。残す価値のある答えは説明ページとして保存する | 変えない | 指示があれば都度 |

### 「意味を変えない」を機械で確かめる

整理で規範の中身がすり替わると、承認を経ない変更が紛れ込む。**`/tidy` の完了条件は
`scripts/validate.sh --normative-diff HEAD` が「規範の差分なし」を返すこと。** この検査は
規範ページの箇条書き・表の行の集まりと、シナリオ ID ごとの名前・本文を比べる(リンクの付け外しと
空白の揺れは無視する)。ページをまたいで移しても、一字も変えなければ差分は 0 になる。
`/decide` では、差分が**その論点のシナリオと行だけ**であることを確かめる。

## 規範ページの書き方(要件定義・基本設計に共通)

- **規範になるのは箇条書き(`- `)と表の行だけ。** 散文は説明として扱う(読みやすさのために書いてよいが、
  規範を散文にだけ書かない)。`--normative-diff` と「規範ページの由来」検査がこの区別で動く。
- **冒頭の frontmatter に由来の論点番号を書く**(`decisions: [0003, 0007]`)。規範の記述があるのに
  由来が無い、または `decided/` に無い番号を指していると `scripts/validate.sh` が NG にする。
  シナリオ ID の先頭4桁の論点もすべて含める。
- **ファイル名・置き場は自由**(`/tidy` が読みやすさのために移してよい)。だから `decided/` の
  `反映先:` にはパスを書かず、**シナリオ ID と設計の項目名**で書く(決定済みの論点は書き換え禁止で、
  パスを書くと移すたびに壊れる — @decision-rules.md「記録の不変性」)。
- 用語は `docs/glossary.md` の語を使う(@impl-rules.md N-1)。

## 要件定義の書き方(`docs/requirements/`)

### 機能要件:GIVEN / WHEN / THEN

- 1要件 = 1見出し(**要件 = 設計上の機能の単位**)。1シナリオ = 後でテスト1メソッドに対応させる。
- **各シナリオに ID を振る**:見出しは `### S<論点番号4桁>_<連番2桁> <シナリオ名>`。ID はテスト名に
  そのまま埋め込み、要件 ↔ test を機械照合する。書式・払い出し・不変性の正本は @impl-rules.md N-2
  (ここに書き写さない)。
- シナリオ名は test メソッド名に流用できる短さにする。

### 必須カバレッジ

- 正常系・異常系・境界(0件、空、上限、同時、リソース枯渇 等)を必ず網羅する。
- **「してはいけない動作」もシナリオにする。** 機能が満たすべき動作(肯定側)だけを書くと、
  実装が**余計なことをしていない**ことを誰も検証できない。異常系(不正な入力が正しくエラーに
  なる)とは別物なので、異常系を書いたから足りている、と扱わない。
  1要件につき次の3種が該当するかを**必ず確認し**、該当するものを THEN に書く。

  | 種類 | 何を否定するか | 例 |
  |---|---|---|
  | 禁止された操作・遷移 | その状況で起きてはならない振る舞い | まひ中は攻撃が合法手に**含まれない** |
  | 対象外への波及 | 効果が及んではならない範囲 | ベンチのポケモンには**付与されない** |
  | 意図しない副作用 | 変わってはならないもの(状態・引数・外部) | 再付与しても状態は**変化しない** |

  3種目は @impl-rules.md N-3 の契約(`apply_*` は純関数で引数を書き換えない等)を
  シナリオに落としたもの。契約を宣言しただけでは守られているか分からない。
- **セキュリティ要件も否定のシナリオにする**(認証なしで拒否される / 他人のデータは返らない /
  エラー応答に内部情報が含まれない 等)。レビューで「ここは安全か」と疑ったことは、テストで
  閉じられる形に書き直す(@security-rules.md「原則」の「ループを閉じる」)。
- 外部効果のあるものは「発動条件」「効果」「失敗時」を分けて書く。
- 曖昧さが残る箇所は `[要確認]` を付け、人間の確定を待つ。勝手に決めない。

### 非機能要件

`docs/requirements/` に非機能要件のページを置き、次の6分類について**該当するかを判定して残す**
(IPA「非機能要求グレード」の大項目。判定していない分類を残さない)。

| 分類 | 例 |
|---|---|
| 可用性 | 稼働時間、障害からの復旧目標 |
| 性能・拡張性 | 応答時間・時間予算、扱う件数の上限 |
| 運用・保守性 | 監視、ログ、バックアップ |
| 移行性 | 既存データ・既存システムからの移行 |
| セキュリティ | 認証・認可、機密の扱い、ログ、検証基準(OWASP ASVS のレベル — @security-rules.md) |
| システム環境・エコロジー | 動作環境、外部サービス、法令・規制、消費電力 |

- **テストで確かめられるもの**(時間予算を超えない、上限で打ち切る、認証なしで拒否する等)は
  機能要件と同じシナリオの形で書く(決定的にテストする — @test-rules.md)。
- **指標でしか測れないもの**(体感の速さ、精度)は要件に数値を書かず、非決定的な論点で計測して決める
  (@experiment-rules.md)。

## 基本設計の書き方(`docs/design/`)

**外部設計まで書き、詳細設計は書かない。** 部品の外から見える約束だけを書き、中の作り方はコードに任せる。

| 節 | 書くこと | 書かないこと |
|---|---|---|
| 構成要素と責務 | 構成要素ごとの責務・持たないもの・依存してよい向き | ファイル分割・クラス構成 |
| 外部との契約 | 入出力の形式・エラーの返し方・設定項目の意味と既定値 | 関数のシグネチャ・内部の型 |
| 概念データモデル | 概念・持つもの・関係・不変条件 | テーブル定義・カラム型 |
| 非機能の実現方針 | 非機能要件をどの構成要素でどう満たすか | チューニング値(config が正本) |
| セキュリティ設計 | 信頼境界・脅威モデル・高リスク領域(下記) | 実装の細部 |

### セキュリティ設計(脅威モデル)

設計の段階で、次の4つの質問に答えて残す(Threat Modeling Manifesto の4つの質問。
OWASP の脅威モデリングの手引きも同じ問いから始める)。

1. **何を作っているか** — 構成要素・データの流れ・**信頼境界**(外部入力・利用者・外部サービス・LLM との境目)
2. **何が問題になりうるか** — 信頼境界ごとの脅威。OWASP の該当項目(@security-rules.md「外部チェックリスト」)
3. **どう対処するか** — 対策と、それを確かめるシナリオ ID
4. **十分にできたか** — 否定のシナリオで確かめたか、残るリスクは何か

あわせて、人間が必ず詳細にレビューする**高リスク領域**(認証・認可・決済・暗号・個人情報・秘密の扱い・
権限設定・CI 設定など)を構成要素の単位で列挙する(レビューの深さ — @security-rules.md)。

## 何を仕様化するか

- **仕様化する**:決定的な振る舞い。コアロジック、状態遷移、エラー処理、境界条件。
  **外部との契約**(入出力のデータ形式・ファイル形式・API の形・設定項目の意味と既定値)も
  ここに入る — 外から見える約束であり、コードの都合で変えてよいものではないため。
  **関数のシグネチャや内部の型はコード側**(上の判定1)。混同しない。
- **仕様化しない**:非決定的な方針(探索・チューニング)。→ 非決定的な論点として
  `decisions/undecided/` に置き、計測で決める(@experiment-rules.md)。
- **混在する処理は境界で分割する**:LLM 呼び出し・乱数を含む処理でも、入出力契約・プロンプト構築・
  パース・検証・エラー処理は決定的なので仕様化する。モデル出力の質・精度・揺れは非決定的なので
  非決定的な論点へ切り出す。迷ったら「同じ入力で2回実行して bit 単位で同一の出力を保証できるか」で判定し、
  保証できない部分だけを探索ループに切り出す。

## 確定の流れ(人間の承認点)

全体像(どのフォルダがどう遷移するか)の図は @architecture.md「決定の流れ」。
ここは**各段で何を書き、誰が何を承認するか**を持つ。

1. `decisions/undecided/NNNN-<論点名>/topic.md` に論点を書く — 何を決めるか / 案 / 比較 /
   現在の考え / `[要確認]`。**冒頭に種別タグ(決定的 / 非決定的)を必ず書く。**
   非決定的なら `config.yaml` と `result.md` を同居させ、計測で決める(@experiment-rules.md)。
   `/ingest` が見つけた食い違いや要件の候補も、ここから始める。
2. 議論して案を絞る。**決まるまで `undecided/` に置いたまま**にする(未決定を隠さない)。
3. **人間が決定を承認したら**、フォルダごと `decisions/decided/` へ移し、`topic.md` に
   決定 / 理由 / 却下した案 / 反映先を書く(理由は CLAUDE.md「エージェントの制約」の同項)。
4. **その場で統合する** — 要件は `requirements/` に GIVEN/WHEN/THEN で、構成要素の責務や契約は
   `design/` に書き起こし、frontmatter の `decisions:` に論点番号を足す。続けて `index.md`・
   `overview.md` を更新し、`log.md` に追記する。**未統合の `decided/` を残さない。**
   シナリオ本文を `decided/` に重複させず、反映先(シナリオ ID と設計の項目名)だけ記す。
   **詳細設計(どのファイル・どの関数に置くか)は文書に書かない** — 結果はコードに現れ、
   理由は `decided/` の論点に残る(上の「どこに何を書くか」)。
5. 統合された `docs/` をもとに `work/NNNN-<作業名>/` を切り、テスト・実装に進む。
   着手には @test-rules.md「着手の許可」が要る。
6. 総合テストまで緑になったら**作業フォルダを削除して閉じる**。何を消し何を残すかは
   @architecture.md「終わり方」が正本(`decisions/` と `docs/` は消さない)。

## topic.md テンプレ(すべての論点で共通)

決定的・非決定的のどちらでもこの形。**`undecided/` の間は「決定」以下を空にしておく**
(未決定を決まったように見せない)。論点の切り方・粒度は @decision-rules.md。

```markdown
# 論点 NNNN: <決めることの名前>

- **種別: 決定的 / 非決定的**   ← 必須。/validate が欠落を NG にする
- **状態: 未決定 / 決定済み**
- **反映先: <要件のシナリオ ID / 基本設計の項目名 / 用語集の語>**(パスは書かない。どれにも及ばないなら `—`)

## 何を決めるか
<決めないと先に進めない事柄。なぜ今これを決める必要があるか>

## 案
| | 案A | 案B |
|---|---|---|
| <比較軸:依存方向 / 変更頻度 / テスト容易性 など> | | |

<!-- 非決定的な論点だけ、ここに「## 測り方」「## 中止条件」を足す
     (書式は @experiment-rules.md「測り方の書式」。決定的な論点には置かない) -->

## 現在の考え
<いまどの案に傾いているか。止まっているなら何を待っているか / いつ再開するか
(@decision-rules.md「決まらないまま止めるとき」。/where がここを読む)。
決定したら節ごと消す — 結論は「決定」、経緯は「理由」「却下した案」に移る>

## [要確認]
- <人間の確定が要る点。解消したら行ごと消し、空になったら節ごと消す。残っている間は /decide が止まる>

## 決定
<採用した案。断定形で1つに絞る。未決定の間は空>

## 理由

## 却下した案
- <案> — <なぜ採らないか>

```

## ページのテンプレ

### 要件定義のページ

```markdown
---
decisions: [<論点番号>]
---
# 要件: <名前>
<1文で何を保証するか(散文 = 説明)>

### S<論点番号>_01 <正常系の名前>
- GIVEN <前提>
- WHEN <操作>
- THEN <期待される結果>

### S<論点番号>_02 <異常系の名前>
- GIVEN ...
- WHEN ...
- THEN ...

### S<論点番号>_03 <境界の名前> [境界]
- GIVEN ...
- WHEN ...
- THEN ...

### S<論点番号>_04 <してはいけない動作の名前> [否定]
- GIVEN ...
- WHEN ...
- THEN <禁止された操作が起きない / 対象外に波及しない / 変わってはいけないものが変化しない>
```

> `[否定]` の見出しは飾りではなく、上の「必須カバレッジ」の3種を確認した形跡として残す。
> 該当が無い要件なら削除してよいが、**確認せずに消さない**。
