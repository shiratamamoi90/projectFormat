# アーキテクチャ:分離軸 × 実装手段

この設計は2つの直交する軸でできている。規模が変わっても **Core は書き換えず、行・列・セル単位で足し引きする**だけで拡張できる。

## 分離軸(縦):規模に応じたレイヤー

| レイヤー | いつ使うか | 内容 |
|---|---|---|
| **Core** | 常時(個人開発から) | 二系統原則、基本 skill、format+test フック |
| **Scale** | 規模が上がったら足す | 危険操作veto、CI連携、sub-agent 並列化 |
| **Adapt** | プロジェクト種別で差替 | 「正」の定義、ドメイン別 skill、`migrations/` や `fixtures/` 等 |

## 実装手段(横):担保の強さ

| 手段 | 置き場 | 強制力 | 役割 |
|---|---|---|---|
| **方針** | CLAUDE.md / .claude/rules/ | なし(影響のみ) | 守ってほしいこと |
| **実行** | .claude/skills/ | コマンドで呼ぶ | 繰り返す工程の自動化 |
| **強制** | .claude/settings.json (hooks) | あり(機械実行) | 絶対に守らせること |

> 右へ行くほど強い。**絶対則は方針列に置いたままにせず、強制列(hooks)か実行列(skill)の停止条件へ
> 移す**(理由は CLAUDE.md「参照先」冒頭)。

## マトリクス

| | 方針 | 実行 | 強制 |
|---|---|---|---|
| **Core** | 二系統原則・Don't | /new-topic, /decide, /new-work, /validate, /run-loop | format on edit, test on stop |
| **Scale** | チーム規約・ロール | /measure, /team-onboarding | 危険操作veto, 時間予算, CI |
| **Adapt** | 「正」の定義・不変条件 | ドメイン別コマンド | ドメイン別検査 |

各セルは独立。1セルの変更が他に波及しない。

実体の所在(このテンプレートに収録済みのもの):
- Core・実行の skill 5つ → `.claude/skills/{new-topic,decide,new-work,run-loop,validate}/SKILL.md`
- Core・強制の hooks(format on edit / test on stop)→ 配線は `.claude/settings.json`、
  実体は `scripts/hooks.sh format` / `scripts/hooks.sh test`
- Scale・強制のうち veto と validate → 配線は `.claude/settings.team.json`(settings.json にマージで
  有効化)、実体は `scripts/hooks.sh veto` / `scripts/hooks.sh validate`
- Scale・実行の /measure /team-onboarding、Scale・強制の時間予算・CI → **未収録**。規模が上がった時に追加する。
- Adapt 行 → 種別確定後に追加する(下の「種別ごとの Adapt」)。テンプレートには**未収録**。

## 決定の流れ(全体像)

```
decisions/undecided/NNNN-<論点>/     案を出し、精査し、議論する
        ↓ 決まったら フォルダごと移す
decisions/decided/NNNN-<論点>/       決定 + 理由 + 却下案 + 反映先
        ↓ その場で統合する(未統合の decided を残さない)
docs/                        何を満たすか(← 正本。どう作るかはコードが正本)
        ↓ 正本をもとに作業単位を切る
work/NNNN-<作業名>/                  tasks / diff(git 追跡外)
        ↓
テスト → 実装
```

**議論・計測・判断は1つの入れ物(`decisions/`)にまとめ、状態(未決定 / 決定済み)を
フォルダで表す。** 状態を文書中のフラグで持つと二重管理になるため、フォルダの移動そのものを
状態遷移にする。

## 二系統の対応表

**二系統は入れ物ではなく論点の属性**になった(フォルダは共通)。`topic.md` 冒頭の
**種別タグが正**で、`scripts/validate.sh` が欠落を検査する。

| | 仕様ループ(決定的) | 探索ループ(非決定的) |
|---|---|---|
| 単位フォルダ | `decisions/{undecided,decided}/NNNN-xxx/`(**共通**) | 同左 |
| 種別の表し方 | `topic.md` 冒頭に「種別: 決定的」 | 「種別: 非決定的」 |
| 決め方 | 案を並べて比較し、根拠で決める | **計測で決める**(`config.yaml` / `result.md` を同居させる) |
| 統合先 | `docs/` に要件として | 決めた値は config へ。理由は論点に残す |
| テスト | 単体で全シナリオ + 総合で経路(主役) | 強さは縛らない。クラッシュ/予算のみ決定的にテスト |
| 対応コード | `src/core`(安定・決定的) | `src/app`(計測して決めた設定を使う側) |

**混ぜない**という原則は変わらない。1つの論点に両方の性質があるなら、決定的な部分と
非決定的な部分を**別の論点に切り分ける**(切り分け方は @doc-rules.md「何を仕様化するか」)。

## 依存方向(不変条件)

```
src/core          ←          src/app
(決定的・安定。純関数中心)      (それを使う側。I/O・UI・探索・評価など)
```
矢印の向きにのみ依存してよい。**層は2つで固定**し、app 側をさらに分けるかは種別次第
(下の「種別ごとの Adapt」)。この図は地図で、規範と崩したときに何が壊れるかは
@impl-rules.md「不変条件」が正本。

## 整合性の優先順位(不変条件)

食い違いを見つけたら、**必ずこの順で上位を正とする**。下位に合わせて上位を書き換えない。

```
ドキュメント  ←  テスト  ←  ソースコード
(仕様が正)      (仕様の写し)   (テストを通すもの)
```

| 順位 | 層 | 実体 | 食い違ったときの扱い |
|---|---|---|---|
| 1 | ドキュメント | `docs/`, `decisions/decided/`, `.claude/rules/`, 「正」(@stack.md) | これが正。直すのは人間の承認を経たときだけ |
| 2 | テスト | `tests/`(単体・総合) | ドキュメントと違えばテストが誤り。仕様に合わせて直す |
| 3 | ソースコード | `src/`, `scripts/` | テストと違えばコードが誤り。テストに合わせて直す |

- **実装に合わせて `docs/` やテストを書き換えない**(最頻出の罠)。コードのほうが正しいと判明した場合も
  順序は変えない:先に論点を開いて人間の承認で `docs/` を直し、次にテスト、最後にコード。
- **確認も同じ順で行う**:ドキュメント同士 → ドキュメント↔テスト → テスト↔コード。
  上位が崩れたまま下位を直しても、直した先がまた誤りになる。
- ドキュメント同士の食い違いは「**正本はどれか**」で解く(コマンドの正本は @stack.md、リポジトリの
  状態の正本は `TEMPLATE.md` 冒頭)。正本が決まっていない事実は、正本を決めてから直す。
- この検査を実行するのが `/validate`(実行列)。

## 種別ごとの Adapt(差し替え表)

| 種別 | 「正」 | 仕様ループ | 探索ループ | 固有物 |
|---|---|---|---|---|
| Web/業務アプリ | 要件定義 | 主役 | ほぼ無し | migrations/ |
| CLI/ツール | コマンド仕様 | 主役 | 無し | fixtures/ |
| ライブラリ | 公開API契約 | 主役 | 無し | 後方互換テスト |
| MLコンペ | 評価指標+ルール | core部のみ | 主役 | baseline 実装 |
| 研究/PoC | 検証仮説 | 補助 | 主役 | data versioning |

### 層の中身も種別で変わる(境界は変えない)

`core` と `app` の**2層と依存の向きは不変**。**何を入れるかだけ**が種別で変わる。

| 種別 | `src/core`(決定的) | `src/app`(それを使う側) |
|---|---|---|
| Web/業務アプリ | ドメインロジック・状態遷移・検証 | HTTP ハンドラ、DB アクセス、UI |
| CLI/ツール | 変換・整形・判定のロジック | 引数解析、ファイル I/O、標準入出力 |
| ライブラリ | 公開する処理の本体 | 薄い(ほぼ無い)。あっても I/O アダプタ程度 |
| MLコンペ | 環境・ルール・評価指標の計算 | 探索・方策(agent)、自己対戦(eval) |
| 研究/PoC | 前処理・指標計算など再現が要る部分 | 実験ドライバ、可視化 |

**app をさらに分けたければ分けてよい**(MLコンペなら `app/agent` と `app/eval` 等)。
ただし**分けた先どうしの依存は core を経由させる** — app 内で相互依存を作ると、
どちらが下位か決まらなくなる。

種別が変わったら Adapt 行だけ差し替える。Core/Scale は不変。
