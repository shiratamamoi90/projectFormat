# 実装のルール(技術・インフラ)

## 技術選定

- 言語 / FW・環境・依存管理は @stack.md「Stack」が正本(ここには重複して書かない。記入スロットも
  stack.md 側にだけ置く)。
- コアロジック(src/engine)は副作用を閉じ込めた純粋関数中心。状態は不変に近い形で受け渡す:
  `apply(state, action) -> new_state`。テストと探索(自己対戦/探索木)の両方で再利用するため。

## 不変条件

以下はプロジェクト全体で崩してはならない。CLAUDE.md からもこの見出しを参照する。

- **依存方向は一方向**:`src/engine`(決定的) ← `src/agent`(探索) ← `src/eval`(評価)。
  engine は agent / eval を import しない。逆向きのみ許す。崩すとテスト容易性と再現性が同時に壊れる。
- **再現性を保つ**:乱数シード・依存バージョンを固定する。再現できない結果は残さない。

## インフラ

最初の2つは不変条件「再現性」を実装でどう満たすかの手段。

- 乱数: シードを config で固定可能にする(直書きしない ← 下の「ハードコード禁止」)。
- 依存: lockfile / requirements でバージョンを固定する。
- 時間予算が要る処理(締切・制限時間)は budget を引数で受け、超過前に最善を返す anytime 設計。

## ハードコード禁止(値は名前と設定に出す)

コードに直書きした値は、**仕様変更時に追随漏れを起こし、探索ループの config で差し替えられなくなる**。
値をどこに置くかは、その値が「誰の都合で変わるか」で決まる。

### 禁止するもの

- **マジックナンバー / マジック文字列**:意味を持つ数値・閾値・上限、状態名などの文字列リテラル。
  名前付き定数にする。目安は「**この値を変えるとき何箇所直すか**」— 2箇所以上なら必ず定数化。
- **環境に依存する値**:パス、URL、ポート、ホスト名、タイムアウト(直書きすると WSL2 / Docker / CI
  で壊れる)。
- **実験で振る値**:探索パラメータ、シード、試行数(直書きすると `experiments/NNNN/config.yaml` で
  1変数だけ変える規律が成立しない。@experiment-rules.md)。
- **秘密情報**:APIキー・トークン・認証情報(扱いは @security-rules.md「機密情報」)。

### 置き場所(上の4種をどこに出すか)

| 値の種類 | 置き場 |
|---|---|
| 「正」由来のドメイン定数(仕様上の固定値) | engine 内の名前付き定数。**出典をコメントで書く**(@stack.md の「正」の該当箇所) |
| 実験で振るパラメータ・シード | config(experiments の config.yaml で上書き可能にする) |
| 環境依存(パス・URL・接続先・予算) | 環境変数 / 設定ファイル |
| 秘密 | 環境変数 / secret manager |

### 例外(直書きが正しいもの)

- **テストの期待値**:テストは仕様の写しなので、期待値はベタ書きする。実装と同じ計算で期待値を
  導出しない(実装のバグをテストがそのまま再現し、検証にならない)。
- **依存バージョン**:lockfile で固定する(上の「不変条件」。むしろ固定が必須)。

```python
# ✗ なぜ 5 なのか、ルール改定時にどこを直せばよいのか分からない
if len(state.bench) >= 5:
    return []

# ○ 名前と出典を与える。変えるのはこの1箇所だけで済む
MAX_BENCH = 5  # 「正」§2.1 のベンチ上限。ルール改定時はここだけ変える
if len(state.bench) >= MAX_BENCH:
    return []
```

## 共通化(重複は「変わる理由」で判断する)

同じ知識が2箇所にあると、片方だけ直して**もう片方が古い仕様のまま残る**。これを防ぐのが共通化。
ただし似ているだけのコードを無理に寄せると、片方の都合で共通部分を変えたときもう片方が壊れる。

### いつ確認するか

- **リファクタ段階(Green の後)**。最小実装の途中で共通化しない。先に緑にしてから、
  テストに守られた状態で寄せる(@test-rules.md のループ手順 3 → 4)。
- change を閉じる前に一度、追加・変更した箇所を見渡し「同じ知識が2箇所以上に無いか」を確認する。

### 共通化する / しない

- **する**:同じ知識(仕様・計算・判定)が複数箇所にある。片方を直したらもう片方も必ず直す関係。
- **しない(偶然の重複)**:今はコードが似ているだけで、**変わる理由が違う**もの。別物として残す。
- 判定は「**片方の仕様が変わったとき、もう片方も必ず変わるか**」。
  必ず変わる = 同じ知識 → 共通化。変わらないことがある = 別物 → 重複のまま残す。
- 2箇所は許容してよいが、**3箇所目が出たら必ず見直す**(設計が要求している合図)。

### どこに置くか(依存方向を崩さない)

置き場は依存方向(engine←agent←eval)で決まる。**共通化のために逆向きの import を作らない。**

| 共有する範囲 | 置き場 |
|---|---|
| engine の中だけ | engine 内の関数に切り出す |
| engine と agent / eval | **engine**(下位)に置く。決定的でないものは engine に入れない |
| agent と eval | agent に置く(eval → agent は順方向) |
| 非決定的な処理を engine と共有したい | 共通化しない。engine は引数で受け取る(注入する) |

- 「共通だから」という理由で上位を import しない。逆向きが必要になったら、**切り出す場所が
  間違っている合図**。不変条件を優先し、共通化のほうを諦めるか設計を変える。

### テストの共通化

- **前提の構築(GIVEN)は共通化する**:`make_state(...)` のようなヘルパ / fixture にまとめる。
- **期待値(THEN)は共通化しない**:各テストに直書きする(上の「ハードコード禁止」の例外)。
  期待値を共通関数で計算すると、実装のバグをテストが再現して検証にならない。

## 命名規則

判断基準は「**読み手が最短時間で理解できるか**」だけ(『リーダブルコード』1章:読みやすさの基本定理)。
好み・短さ・タイプ量で決めない。ここに置くのは**言語非依存**のルール。snake_case などの記法は
言語ごとに異なるので @stack.md「命名の記法」に置く。

### N-1 用語の「正」は `specs/glossary.md`

- 仕様に登場する概念はすべて `specs/glossary.md` に登録する。
  **登録されていない語をコードのドメイン語彙として使わない。**
- **名詞形が正。** データ・enum 値・型名・ファイル名・モジュール名は名詞形から作る。
- 述語(ブール)が必要なときだけ形容詞形を使い `is_<形容詞形>` にする。
  「まひ」は名詞形 `paralysis` が正、述語は `is_paralyzed`。**`is_paralysis` は禁止**(名詞形の誤用)。
- 形容詞形が無い語(`—`)で述語が要るときは `has_<名詞形>` にする。
- **同義語を作らない。** 同じ概念に2語出てきたら実装で吸収せず spec 側を1語に直す。
- 用語の追加・変更・削除は仕様変更。`changes/NNNN-*/` を通す。

**なぜ**:同じ概念が `paralysis` / `para` / `ailment` と揺れると、読み手は「別物かもしれない」と疑って
定義を追跡し直す(1章)。正を1箇所に置けば揺れは機械検査で落とせる(N-8)。

### N-2 シナリオ ID `S<4桁>_<2桁>`

- 書式は `S<change 番号4桁>_<連番2桁>`。例 `S0001_01`。
- **ハイフンを使わない。** 全言語で識別子の一部に使えるようにするため
  (`S-0001-01` はテスト関数名に埋め込めず、照合が言語依存になる)。
- ID は払い出したら**不変**。change をまたいで再利用しない。仕様が廃止されても欠番のまま残す。
- `spec.md` の各シナリオ見出しを `### S0001_01 <日本語のシナリオ名>` にする。
- テスト名に**この ID を一字も改変せずそのまま含める**。前後のケース記法は言語規約に従ってよい。

  ```
  Python  def test_S0001_02_paralyzed_actor_cannot_attack():
  Java    void S0001_02_paralyzedActorCannotAttack()
  TS      it('S0001_02 paralyzed actor cannot attack', ...)
  ```

- **ID だけのテスト名は禁止。** ID の後に「何を検証するか」を用語集の語で続ける。
- **1シナリオ = 1テスト関数。** 複数の THEN を1関数にまとめない(11章:一度に1つのことを)。
- **ID を書くのはテスト関数名だけ。** 同じファイルのコメント・docstring に重ねて書かない
  (N-8 の重複検査が誤検出する)。
- **総合テスト(tests/integration/)には ID を付けない。** 総合テストはシナリオではなく経路を
  検証するため(@test-rules.md)。付けると1シナリオ1テストの重複検査に掛かる。

**なぜ**:仕様とテストの対応を人間の記憶ではなく文字列一致で保証するため。日本語のシナリオ名だけでは
表記揺れで照合できず、機械検査が書けない。ID を不変にするのは、番号が動くと過去の result・
コメント・ADR からの参照が一斉に壊れるため。

### N-3 関数の接頭辞と契約

engine の公開 API には**この表の動詞だけ**を使う。表に無い動詞を新設しない。

| 接頭辞 | 契約 | 返り値 | 副作用 |
|---|---|---|---|
| `apply_*` | 状態に規則を適用する | 新しい状態 | 禁止(純関数。引数を書き換えない) |
| `get_*` | 保持している値をそのまま返す | 値 | 禁止。重い計算をしない |
| `compute_*` | 計算して値を作る | 値 | 禁止 |
| `resolve_*` | 複数候補から1つ決める | 選ばれた値 | 禁止 |
| `is_*` / `has_*` / `can_*` / `should_*` | 判定する | bool のみ | 禁止。例外を投げない |
| `validate_*` | 不正を検出する | エラーの一覧(空なら正常) | 禁止。bool を返さない |
| `build_*` / `make_*` | 組み立てる | 生成物 | 禁止 |
| `load_*` / `save_*` / `send_*` | 外界と入出力する | 任意 | **許可(ここだけ)** |

- `apply_*` を破壊的にしたくなったら**設計が誤り**。表で副作用を許した3つ(`load_*` / `save_*` /
  `send_*`)は engine の外側(境界)に置く。engine が決定的でなくなると依存方向の不変条件が壊れる
  (@architecture.md「依存方向(不変条件)」、上の「技術選定」の純粋関数中心の方針)。
- `get_*` を見た読み手は O(1) を期待する(3.8:ユーザの期待に合わせる)。計算するなら `compute_*` に分ける。
- **名詞止まりの関数名を禁止。** `accuracy_check()` は bool か例外か結果オブジェクトか判別できない。
  用語集の名詞は概念・データ・型の名前であって関数名ではない(判定なら `resolve_accuracy_check`)。
- `validate_*` が bool を返さないのは、「何が不正か」を呼び出し側が報告できるようにするため。

### N-4 ブール値

- `is_` / `has_` / `can_` / `should_` のいずれかで始める。他の接頭辞を使わない。
- **否定形を名前に入れない。** `is_not_paralyzed` / `disable_x` / `skip_x` は禁止。
  肯定形(`is_paralyzed` / `enable_x`)を定義し、呼び出し側で否定する。

**なぜ**:否定形は `if not is_not_paralyzed` のような二重否定を生み、読み手が毎回頭の中で
反転させることになる(3.7:ブール値の名前)。

### N-5 範囲・限界・単位

| 意味 | 使う名前 | 根拠 |
|---|---|---|
| 上限・下限(その値を含む) | `max_*` / `min_*` | 3.4 |
| 範囲で両端を含む | `first_*` / `last_*` | 3.5 |
| 範囲で終端を含まない | `*_begin` / `*_end` | 3.6 |
| 単位を持つ数値 | `<名前>_<単位>`(`duration_turns`, `timeout_ms`)。**単位なしを禁止** | 2.4 |
| 未加工 / 正規化済み | `raw_*` / `normalized_*` | 2.1 |

両義的な語は使わず、次の言い換えを使う(3.2 / 3.3)。

| 使わない | 使う |
|---|---|
| `filter_*` | `select_*`(残す) / `exclude_*`(除く) |
| `clip_*` | `truncate_*`(末尾を切る) / `clamp_*`(範囲に収める) |
| `length` | `char_count` / `byte_size` / `item_count` |
| `check_*` | N-3 の表から選ぶ(`is_*` / `validate_*` / `compute_*`) |

**なぜ**:`filter` は「残す」とも「除く」とも読め、`length` は文字数・バイト数・要素数のどれか
決まらない。読み手が実装を読みに行った時点で名前が失敗している。

### N-6 略語

- **ドメイン用語は絶対に略さない。** `paralysis` → `para` / `plz` は禁止(用語集の禁止表記に登録する)。
- 使ってよい汎用略語は次のホワイトリストだけ。**これ以外を新規に作らない**:

  `id, uuid, url, uri, http, json, yaml, csv, db, sql, api, io, ui, cli, env, cfg, ctx,`
  `max, min, num, idx, src, dst, req, res, ms, kb, mb`

- `i` / `j` / `k` はスコープが数行に収まるループ変数のみ許可。
- **名前の長さはスコープに比例させる**(2.5)。生存が長い識別子ほど長い名前にする。
- 中身のない名前を単独で使わない:`tmp` `data` `result` `value` `obj` `info` `manager` `helper` `util`。
  例外は**生存3行以内の `tmp` のみ**(2.2)。

### N-7 ファイル・モジュール

- ソースファイル名は、そのファイルの主要概念の**用語集の名詞形**から作る。
- `util` / `helper` / `manager` を含むファイル名を禁止(`status_utils` など)。
  何を入れてよいか決まらず、無関係なコードの置き場になって肥大化する。
- テストファイルは対象ファイルと**1対1**。1実装ファイルに複数のテストファイルが対応する、または
  1テストファイルが複数の実装ファイルを見る状態になったら、**実装の分割が誤り**(11章)。

### N-8 機械検査

次の7つは `scripts/validate.sh` が機械判定する(人間のレビューに委ねない)。
検査項目を増やしたらこのリストとスクリプトを同時に直す(片方だけ直すと正本が2つになる)。

1. **spec の書式** — シナリオ見出しが `### S<4桁>_<2桁> <名前>` の形式で、GIVEN / WHEN / THEN が
   揃っている(N-2 / @spec-rules.md「書式」)。
2. **ID の払い出し** — 同じシナリオ ID を2つの見出しが持たない。ID の先頭4桁が change フォルダの
   連番と一致する(N-2)。
3. **用語集の書式** — `specs/glossary.md` の `## 用語` テーブルが5列固定(下の 4. が列位置で
   「使ってはいけない表記」を読むため、先に形を検査する。N-1)。
4. **用語の揺れ** — 用語集の「使ってはいけない表記」が `src/` `tests/` に出現しない(N-1)。
5. **spec ↔ test 対応** — シナリオ ID を双方向照合。spec にあって test に無い = 未実装、
   test にあって spec に無い = 幽霊テスト(N-2)。
6. **1シナリオ1テスト** — `tests/` 側で同じ ID が重複しない(N-2)。
7. **否定形ブール** — `is_not_*` 等が存在しない(N-4)。

記法(snake_case 等)はここで検査しない。フォーマッタ/リンタを hooks で自動実行して機械的に落とす
(手動整形しない。@stack.md「命名の記法」)。

## コメント:「何」は一言・「なぜ」を厚く

コードは「何をしているか」を既に語っている。コメントが埋めるべきは**コードに書けない「なぜ」**。

- **「何について」は一言で済ませる。** 処理を逐語訳するコメント(`# i を 1 増やす`)は書かない。
  engine の各ロジックには、対応する spec シナリオ名をその一言として必ず付ける(下の例の1行目)。
- **「なぜその処理にしたか」はしっかり書く。** 次に読む人が知らないと壊してしまう前提を残す:
  - **選ばなかった実装とその理由**:より自明に見える書き方をなぜ採らなかったか。
  - **根拠にした制約**:「正」(@stack.md)の該当箇所、外部仕様・データ契約の都合、
    性能や時間予算の要求。根拠の出典を書く(「仕様書 §4.2 より」など)。
  - **意図的にやっていないこと**:対応範囲外と判断した条件、既知のトレードオフ。
- 迷ったら「**この行を消すと何が壊れるか**」を書く。それが「なぜ」にあたる。
- 「なぜ」が数行に収まらない、または複数箇所に影響する判断は、コメントに書かず
  `decisions/` の ADR に書き、コメントからは ADR 番号だけ参照する(コメントの肥大化を防ぐ)。
- 「誰が・いつ・どの依頼で書いたか」は書かない(履歴は git が持つ)。残すのは判断の理由だけ。

```python
# S0001_02 まひ中は攻撃・逃げ不可          ← 何について(一言。シナリオ ID + 名前)
#
# なぜ合法手の生成側で落とすか:実行時に弾く実装にすると、探索(src/agent)が
# 非合法手を候補に入れたまま木を広げ、engine と agent で合法手の定義が
# 二重管理になる。合法手の定義は engine だけが持つ(不変条件:依存方向)。
# 逃げも同時に禁じるのは「正」の状態異常セクションの規定による。
def get_legal_actions(state: BattleState) -> list[Action]:
    ...
```
