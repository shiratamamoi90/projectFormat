# セキュリティのルール

決定的/非決定的のどちらのループでも守る横断ルール。CLAUDE.md からこのファイルを参照する。
プロジェクト固有の脅威モデルがあれば「## このプロジェクト固有」に追記する。

## 機密情報

- 秘密情報(APIキー・トークン・認証情報・個人情報)を**コード・`docs/`・`decisions/`・ログ・
  コミットに残さない。** `decisions/` は git 追跡対象なので、議論の途中の書き込みもそのまま共有される。
- 秘密は環境変数か secret manager から読む。`.env` 等はコミットしない。
- **除外は `.gitignore` で担保する。その `.gitignore` はプロジェクト開始時に `gitignore.template` を
  リネームして作る**(`DEVELOPMENT.md`「プロジェクト開始の手順」手順1)。`.env` `.env.*` はその区分1に入っている。
  **リネーム前は除外が一切効かない**ため、最初のコミット前に必ず済ませる(フォーマット本体の
  リポジトリだけは同梱物ごと管理する都合で `.gitignore` が空 = 除外なしが正)。
- `decisions/` の `result.md` / `topic.md` に生データや個人情報を貼らない。必要なら匿名化・集計値のみ。
- **`work/` が git 追跡外なのは共有不要だからで、安全だからではない。** 秘密をそこに置かない
  (ローカルに平文で残り、バックアップや別ツール経由で漏れる)。

## 危険操作(強制と対応)

- 破壊的・不可逆な操作(`rm -rf`、`git push --force`、本番へのマイグレーション/削除)は人間の承認なしに実行しない。
- `rm -rf` と `git push --force` は hooks の veto(@architecture.md の「強制」列)で機械的に止める。
  実体は `scripts/hooks.sh veto`、配線は settings.team.json。veto は Scale 層のため、
  settings.team.json を settings.json にマージして初めて有効になる。**マージのしかたは
  settings.team.json の `_comment` が正本** — `Stop` は両方のファイルにあるので、
  置き換えると Core の停止時テストが黙って消える。**追記してから両方の発火を確認する。**
- 本番マイグレーション・削除などプロジェクト固有の危険コマンドは、同じスクリプトの
  `DANGEROUS_PATTERNS` にパターンを追記して止める(方針に書くだけでは強制にならない)。
- veto を変えたら**必ず発火を確認する**:サンプル入力を流して exit 2 が返ることを見る
  (`echo '{"tool_input":{"command":"rm -rf x"}}' | scripts/hooks.sh veto`)。
  止まらない veto は、止めているつもりで素通りするため方針より危険。
- 外部に送信・公開する操作(デプロイ、外部APIへの送信、issue/PR作成)は事前に確認する。一度出したものは取り消せない前提で扱う。

## 依存・サプライチェーン

- バージョン固定は @impl-rules.md「不変条件」。ここで足すのは**入れる前の審査**で、無審査で
  新規依存を増やさない。出所・メンテ状況を確認し、既存で足りるものを重複させない。
- **新規依存の採用は論点として記録する**(@decision-rules.md「必ず論点として記録するもの」)。
  審査の結果(なぜこれを選び、何を却下したか)はコードに残らないので、`decisions/` に残す。

## 入力と信頼境界

- 外部入力(ユーザー入力・ファイル・ネットワーク)は**決定的なコアに入る手前の境界で検証する**。
  検証そのものは決定的なので、`docs/` にシナリオを書き、テストで縛る。
- 文字列を組み立ててシェル/SQL/コードを実行しない(インジェクション回避)。パラメータ化する。

## 最小権限

- トークン・鍵・DB権限は必要最小限のスコープにする。
- CI / hooks が使う認証情報も同様。読み取りで済むものに書き込み権限を与えない。

## 外部チェックリスト(OWASP)

**リストの正本は外部に置き、ここに全項目を書き写さない**(OWASP は改訂される。写すと古いまま残る)。

- Web・API・データを外部に晒すなら **OWASP Top 10**
- LLM を製品に組み込むなら **OWASP Top 10 for LLM Applications**

**プロジェクト開始時に、各項目が自プロジェクトに該当するかを判定し、下の「このプロジェクト固有」に
記録する。** 該当するのに対策していない項目は、**論点として `decisions/` に開く**
(@decision-rules.md「必ず論点として記録するもの」— 後から「なぜ対策しなかったか」が要る)。
該当しないなら「該当なし」と理由を書く。**判定していない状態を残さない。**

上のルールで既にカバーしているのは、インジェクション(パラメータ化)/ 脆弱な依存(審査・
バージョン固定)/ 機密の取り扱い / 最小権限 / 危険操作の veto。
**それ以外は下の最低限を満たしたうえで、外部リストで確認する。**

### Web・API を作るときの最低限

- **認可は毎回サーバ側の境界で検証する。** UI で隠す・クライアントで判定するだけにしない。
  識別子を受け取る操作は「その利用者がその対象を操作してよいか」を必ず確かめる。
- **認証**:パスワードはハッシュ化して保存し、セッション/トークンに失効と再発行の経路を用意する。
  **自作の認証・暗号を書かない。**
- **暗号**:転送時は TLS、保存時の機密は暗号化。アルゴリズムと鍵はライブラリ既定に従う。
- **設定**:本番でデバッグ機能・詳細エラーを無効化する。**エラー応答に内部情報(スタック・
  クエリ・パス)を出さない。** 既定の管理者アカウントや初期パスワードを残さない。
- **外部宛のリクエスト**:利用者から受け取った URL にサーバがそのままアクセスしない。
  必要なら**宛先を許可リストで固定**する(内部ネットワークへ到達させない)。
- **監査ログ**:認証・権限変更・破壊的操作の成否を記録する。**秘密そのものは書かない**
  (上の「機密情報」)。

### LLM を組み込むときの最低限

**ここでの対象は「作る製品が使う LLM」。** CLAUDE.md の「着手の許可」や危険操作 veto は
**開発を手伝うエージェントへの制約**であって、製品側の対策ではない。**混同しない。**

- **プロンプトに入る外部入力は、信頼境界を越えたものとして扱う。** 利用者入力・取得した
  Web ページ・ファイル・ツールの戻り値はすべて「指示を含みうるデータ」であり、
  **命令として解釈させない**(役割を分離し、指示は開発側の系から与える)。
- **モデル出力をそのまま実行・埋め込みしない。** コード・SQL・シェル・HTML として扱う前に
  検証する。出力の検証は決定的なので `docs/` に書いてテストで縛る。
- **モデルに秘密を渡さない。** 秘密・個人情報をプロンプトや文脈に入れない。外部に送ったものは
  取り消せない(上の「危険操作」)。
- **エージェントに与える権限を最小にする。** ツール・鍵・到達範囲を必要最小限にし、
  破壊的操作は人間の承認を挟む。
- **消費に上限を置く。** 入力長・呼び出し回数・時間予算を決め、超過時に打ち切る
  (@impl-rules.md「インフラ」の budget 設計)。上限はテストで縛る(@test-rules.md)。
- **モデル・データセットにも出所の審査を行う**(上の「依存・サプライチェーン」と同じ)。
