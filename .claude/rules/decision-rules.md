# 決定のルール(論点の切り方・記録・承認)

論点をどう切り、どう記録し、誰が承認するか。**何を書くか**は @requirement-rules.md
「どこに何を書くか」が正本(ここに書き写さない)。流れの図は @architecture.md「決定の流れ」。

## 必ず論点として記録するもの

**コードを読めば分かることは書かない。** ただし次は、結果がコードに現れていても
**「なぜそうしたか」がコードから消える**ので、必ず論点として残す
(コード中のコメント1〜2行で済ませない)。

- 後から変えると **2つ以上の作業に波及する**(層の割り当て、公開する契約、データ形式)
- **不変条件に触れる**(依存方向・再現性)。触れてでも必要だと判断したなら、理由を必ず残す
- **候補が複数あり、選んだ理由がコメント1〜2行に収まらない**(@impl-rules.md「コメント」)
- **外部依存を新しく入れる**(@security-rules.md「依存・サプライチェーン」の審査結果もここに残す)
- 後から「なぜこうなっているのか」と訊かれる可能性が高い

**構造そのものは書かない。** 「`status.py` に置いた」はコードを見れば分かる。
残すのは「**なぜ合法手の生成側に置き、実行時に弾く案を採らなかったか**」。

## 論点を切り分ける粒度

**1論点 = 1つの決めごと。** 迷ったら「この決定だけを後から覆せるか」で判断する。
覆すのに他の決定も一緒に動かす必要があるなら、それらは同じ論点。

- **決定的な論点と非決定的な論点を1つにまとめない。** 両方の性質があるなら分ける
  (@architecture.md「二系統の対応表」。`/validate` が種別タグの欠落を NG にする)。
- 仕様に関わる論点と、その前提になる論点も分ける。**前提が決まる前に先の論点を決めない。**

## 記録の不変性

決定済み論点は**判断の記録**であって作業の記録ではない(作業は `work/`)。

- **`decided/` に移した論点は書き換えない。** 覆すときは**新しい論点を開き**、前のものに
  「論点 NNNN で置き換えた」と1行だけ追記する。議論をやり直した経緯が消えないようにするため。
- **番号は払い出したら不変**(理由は @impl-rules.md N-2 と同じ。シナリオ ID の先頭4桁が
  論点番号なので、番号が動くと要件・テスト・コメントからの参照が一斉に壊れる)。

## 承認点(人間が決めること)

- **決定の承認**:論点を `decided/` へ移し `requirements/` へ統合してよいかを、人間が承認する。
  各段の手順は @requirement-rules.md「確定の流れ」。
- 実装・テストの作成と実行には、さらに @test-rules.md「着手の許可」が要る(別の関門)。
- 迷った点は `[要確認]` を付けて人間に投げる。**勝手に決めない。**

## 決定を変えたくなったとき

- 実装中に「この決定では通らない」と分かっても、**実装に合わせて決定を黙って変えない。**
  止まって新しい論点を開き、承認を取り直す(@architecture.md「整合性の優先順位」)。
- 同じ知識が**3箇所目**に出たら設計が要求している合図(@impl-rules.md「共通化」)。
  その見直しも判断なので、論点として `undecided/` に開く。
- `apply_*` を破壊的にしたくなった、共通化のために逆向きの import が要る — これらは
  **設計が誤っている合図**であって、不変条件を緩める理由にはならない(@impl-rules.md)。
