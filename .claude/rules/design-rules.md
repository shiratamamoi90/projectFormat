# 設計のルール(どう分けて満たすかを決める)

仕様(**何を**満たすか)は @spec-rules.md、設計(それを**どの部品にどう分けて**満たすか)はここ。

**崩してはいけない制約**(依存方向・命名・共通化・整合性の優先順位)は @impl-rules.md と
@architecture.md が正本で、ここに書き写さない。このファイルが持つのは
**決め方・記録先・承認点**の3つだけ。

## 何が設計判断か

次を決めたら設計判断。1関数の中の書き方は含まない(それは実装)。

- **部品の境界**:どのモジュール / ファイルに置くか。新しく作るか、既存に足すか
- **層の割り当て**:engine / agent / eval のどこに置くか(@impl-rules.md「不変条件」の依存方向)
- **契約**:公開する関数の名前と責務(N-3)、入出力の形、状態の持ち方
- **外部との境界**:I/O・外部サービス・永続化をどこで行うか(engine の外に出す)
- **技術の採用**:ライブラリ・データ形式・アルゴリズムの選択

## いつ設計の論点を開くか

手順そのものは他の論点と同じ(図は @architecture.md「決定の流れ」、各段の中身と承認点は
@spec-rules.md「確定の流れ」)。**設計に固有なのはタイミングだけ。**

**仕様が決まる前に設計しない。** 何を満たすか未定のまま部品を割ると、仕様が動いたときに
分割ごと作り直しになる。設計の論点は、対応する仕様の論点が `decided/` に入ってから開く。

## 論点を切り分ける粒度

**1論点 = 1つの決めごと。** 迷ったら「この決定だけを後から覆せるか」で判断する。
覆すのに他の決定も一緒に動かす必要があるなら、それらは同じ論点。

次のどれかに当てはまるものは、**必ず独立した論点として記録する**(コード中のコメントで済ませない)。

- 後から変えると **2つ以上の作業に波及する**(層の割り当て、公開契約、データ形式)
- **不変条件に触れる**(依存方向・再現性)。触れてでも必要だと判断したなら、理由を必ず残す
- **候補が複数あり、選んだ理由がコメント1〜2行に収まらない**(@impl-rules.md「コメント」)
- **外部依存を新しく入れる**(@security-rules.md「依存・サプライチェーン」の審査結果もここに残す)
- 後から「なぜこうなっているのか」と訊かれる可能性が高い

決定済み論点は**判断の記録**であって作業の記録ではない(作業は `work/`)。

- **`decided/` に移した論点は書き換えない。** 覆すときは**新しい論点を開き**、前のものに
  「論点 NNNN で置き換えた」と1行だけ追記する。議論をやり直した経緯が消えないようにするため。
- **番号は払い出したら不変**(理由は @impl-rules.md N-2 と同じ。シナリオ ID の先頭4桁が
  論点番号なので、番号が動くと spec・テスト・コメントからの参照が一斉に壊れる)。

## 承認点(人間が決めること)

- **設計の決定の承認**:設計の論点を `decided/` へ移し `design/` へ統合してよいかを、人間が承認する。
  **仕様の決定の承認とは別**。仕様は「何を作るか」の合意、設計は「どう分けて作るか」の合意で、
  **両方要る**。片方だけで `work/` を切らない。
- 実装・テストの作成と実行には、さらに @test-rules.md「着手の許可」が要る(これで3つ目の関門)。
- 迷った点は `[要確認]` を付けて人間に投げる。**勝手に決めない**(@spec-rules.md と同じ扱い)。

## 設計を変えたくなったとき

- 実装中に「この分割では通らない」と分かっても、**実装に合わせて設計を黙って変えない。**
  止まって、変更後の設計案を出し、承認を取り直す(@architecture.md「整合性の優先順位」)。
- 同じ知識が**3箇所目**に出たら設計が要求している合図(@impl-rules.md「共通化」)。
  その見直しも設計判断なので、新しい論点として `undecided/` に開く。
- `apply_*` を破壊的にしたくなった、共通化のために逆向きの import が要る — これらは
  **設計が誤っている合図**であって、不変条件を緩める理由にはならない(@impl-rules.md)。

## 設計の論点で特に埋めるところ

論点フォルダの置き方・種別タグ・`topic.md` の書式は @spec-rules.md「topic.md テンプレ」が正本
(すべての論点で共通なので、ここに書き写さない)。設計の論点では次を具体的に書く。

- **案の比較軸**:依存方向を崩さないか / 変更頻度 / テスト容易性 / 置き換えやすさ。
- **反映先**:`design/<ファイル>`。仕様にも及ぶなら `specs/<ファイル>` も併記する。
- **却下した案**:「なぜ採らないか」を制約(不変条件・「正」・予算)に紐づけて書く。
