# 設計のルール(どう分けて満たすかを決める)

仕様(**何を**満たすか)は @spec-rules.md、設計(それを**どの部品にどう分けて**満たすか)はここ。

**崩してはいけない制約**(依存方向・命名・共通化・整合性の優先順位)は @impl-rules.md と
@architecture.md が正本で、ここに書き写さない。このファイルが持つのは
**決め方・記録先・承認点**の3つだけ。

## 何が設計判断か

次を決めたら設計判断。1関数の中の書き方は含まない(それは実装)。

- **部品の境界**:どのモジュール / ファイルに置くか。新しく作るか、既存に足すか
- **層の割り当て**:engine / agent / eval のどこに置くか(@impl-rules.md「不変条件」の依存方向)
- **契約**:公開する関数の名前と責務(N-3)、入出力の形、状態の持ち方
- **外部との境界**:I/O・外部サービス・永続化をどこで行うか(engine の外に出す)
- **技術の採用**:ライブラリ・データ形式・アルゴリズムの選択

## 決める順(仕様の後、実装の前)

1. **spec が確定していること。仕様が決まる前に設計しない。** 何を満たすか未定のまま部品を割ると、
   仕様が動いたときに分割ごと作り直しになる。
2. `proposal.md` の「設計案」に書く(下のテンプレ)。**採らなかった案と、その理由を必ず残す。**
   理由が無いと、後から同じ案が再提案されて同じ議論を繰り返す。
3. 重い判断は ADR に切り出す(下の「ADR を書く条件」)。
4. **人間が設計案を承認するまで実装に入らない**(下の「承認点」)。

## ADR を書く条件(1つでも該当したら書く)

置き場は `decisions/NNNN-<名前>.md`。**規模ではなく判断の重さで決める**
(「個人だから任意」という判断をしない。後で読むのは規模が変わった後の自分)。

- 後から変えると **2つ以上の change に波及する**(層の割り当て、公開契約、データ形式)
- **不変条件に触れる**(依存方向・再現性)。触れてでも必要だと判断したなら、理由を必ず残す
- **候補が複数あり、選んだ理由がコメント1〜2行に収まらない**(@impl-rules.md「コメント」)
- **外部依存を新しく入れる**(@security-rules.md「依存・サプライチェーン」の審査結果もここに残す)
- 後から「なぜこうなっているのか」と訊かれる可能性が高い

ADR は**判断の記録**であって変更の記録ではない(変更は `changes/`)。

- **一度書いた ADR は書き換えない。** 覆すときは新しい ADR を書き、前のものを「置き換えた」と記す。
- **番号は払い出したら不変**(理由は @impl-rules.md N-2 と同じ。参照が一斉に壊れるため)。

### ADR テンプレ

```markdown
# ADR NNNN: <判断の名前>

## 文脈
<なぜこの判断が必要か。制約・前提・関係する要件やシナリオ ID>

## 決定
<採用した選択肢。断定形で1つに絞って書く>

## 採らなかった案
- <案> — <なぜ採らないか>

## 結果
- 利点: <この判断で何が良くなるか>
- 欠点 / トレードオフ: <何を諦めたか。後で問題になりうる点>
- 影響範囲: <触る層・ファイル。依存方向を崩していないか>
```

## 承認点(人間が決めること)

- **設計案の承認**:`proposal.md` の設計案(と、あれば ADR)を人間が承認するまで実装に入らない。
  **spec の承認とは別**。spec の承認は「何を作るか」の合意、設計案の承認は「どう分けて作るか」の合意で、
  **両方要る**。片方だけで進めない。
- 実装・テストの作成と実行には、さらに @test-rules.md「着手の許可」が要る(これで3つ目の関門)。
- 迷った点は `[要確認]` を付けて人間に投げる。**勝手に決めない**(@spec-rules.md と同じ扱い)。

## 設計を変えたくなったとき

- 実装中に「この分割では通らない」と分かっても、**実装に合わせて設計を黙って変えない。**
  止まって、変更後の設計案を出し、承認を取り直す(@architecture.md「整合性の優先順位」)。
- 同じ知識が**3箇所目**に出たら設計が要求している合図(@impl-rules.md「共通化」)。
  その見直しも設計判断なので、上の「決める順」を通す。
- `apply_*` を破壊的にしたくなった、共通化のために逆向きの import が要る — これらは
  **設計が誤っている合図**であって、不変条件を緩める理由にはならない(@impl-rules.md)。

## proposal.md の設計案テンプレ

`proposal.md` 全体の構成は @spec-rules.md「確定の流れ」が正本。この節はその「設計案」の中身。

```markdown
## 設計案
- 採る案: <どの層のどのファイルに何を置くか。新規 / 既存の別>
- 採らなかった案: <案> — <なぜ採らないか>
- 影響する層: <engine / agent / eval のどこに触るか。依存方向を崩していないか>
- ADR: <必要なら decisions/NNNN。不要と判断したならその理由を1行>
```
