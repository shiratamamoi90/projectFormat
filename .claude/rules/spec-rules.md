# 仕様設計のルール(決定的部分)

## 何を仕様化するか

- **仕様化する**:決定的な振る舞い。コアロジック、状態遷移、入出力契約、エラー処理、境界条件。
- **仕様化しない**:非決定的な方針(探索・チューニング)。→ experiments/ の hypothesis に書く。
- **混在する処理は境界で分割する**:LLM 呼び出し・乱数を含む処理でも、入出力契約・プロンプト構築・
  パース・検証・エラー処理は決定的なので仕様化する。モデル出力の質・精度・揺れは非決定的なので
  hypothesis へ。迷ったら「同じ入力で2回実行して bit 単位で同一の出力を保証できるか」で判定し、
  保証できない部分だけを探索ループに切り出す。

## 書式:GIVEN / WHEN / THEN

- 1要件 = 1見出し(**要件 = 設計上の機能の単位**)。1シナリオ = 後でテスト1メソッドに対応させる。
- **各シナリオに ID を振る**:見出しは `### S<change番号4桁>_<連番2桁> <シナリオ名>`。ID はテスト名に
  そのまま埋め込み、spec ↔ test を機械照合する。書式・払い出し・不変性の正本は @impl-rules.md N-2
  (ここに書き写さない)。
- シナリオ名は test メソッド名に流用できる短さにする。用語は `specs/glossary.md` の語を使う(N-1)。

## 必須カバレッジ

- 正常系・異常系・境界(0件、空、上限、同時、リソース枯渇 等)を必ず網羅する。
- **「してはいけない動作」もシナリオにする。** 機能が満たすべき動作(肯定側)だけを書くと、
  実装が**余計なことをしていない**ことを誰も検証できない。異常系(不正な入力が正しくエラーに
  なる)とは別物なので、異常系を書いたから足りている、と扱わない。
  1要件につき次の3種が該当するかを**必ず確認し**、該当するものを THEN に書く。

  | 種類 | 何を否定するか | 例 |
  |---|---|---|
  | 禁止された操作・遷移 | その状況で起きてはならない振る舞い | まひ中は攻撃が合法手に**含まれない** |
  | 対象外への波及 | 効果が及んではならない範囲 | ベンチのポケモンには**付与されない** |
  | 意図しない副作用 | 変わってはならないもの(状態・引数・外部) | 再付与しても状態は**変化しない** |

  3種目は @impl-rules.md N-3 の契約(`apply_*` は純関数で引数を書き換えない等)を
  シナリオに落としたもの。契約を宣言しただけでは守られているか分からない。
- 外部効果のあるものは「発動条件」「効果」「失敗時」を分けて書く。
- 曖昧さが残る箇所は `[要確認]` を付け、人間の確定を待つ。勝手に決めない。

## 確定の流れ(人間の承認点)

1. `proposal.md`(なぜ変えるか / ADDED・MODIFIED の影響範囲)を書く。
2. `spec.md`(GIVEN/WHEN/THEN)を書く。
3. **人間が spec を承認するまで実装に進まない**(理由は CLAUDE.md「エージェントの制約」の同項)。

## spec.md テンプレ

```markdown
# 要件: <名前>
<1文で何を保証するか>

### S<change番号>_01 <正常系の名前>
- GIVEN <前提>
- WHEN <操作>
- THEN <期待される結果>

### S<change番号>_02 <異常系の名前>
- GIVEN ...
- WHEN ...
- THEN ...

### S<change番号>_03 <境界の名前> [境界]
- GIVEN ...
- WHEN ...
- THEN ...

### S<change番号>_04 <してはいけない動作の名前> [否定]
- GIVEN ...
- WHEN ...
- THEN <禁止された操作が起きない / 対象外に波及しない / 変わってはいけないものが変化しない>
```

> `[否定]` の見出しは飾りではなく、上の「必須カバレッジ」の3種を確認した形跡として残す。
> 該当が無い要件なら削除してよいが、**確認せずに消さない**。
