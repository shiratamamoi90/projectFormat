# 仕様のルール(論点の確定 → `specs/` への統合)

## 何を仕様化するか

- **仕様化する**:決定的な振る舞い。コアロジック、状態遷移、入出力契約、エラー処理、境界条件。
- **仕様化しない**:非決定的な方針(探索・チューニング)。→ 非決定的な論点として
  `decisions/undecided/` に置き、計測で決める(@experiment-rules.md)。
- **混在する処理は境界で分割する**:LLM 呼び出し・乱数を含む処理でも、入出力契約・プロンプト構築・
  パース・検証・エラー処理は決定的なので仕様化する。モデル出力の質・精度・揺れは非決定的なので
  非決定的な論点へ切り出す。迷ったら「同じ入力で2回実行して bit 単位で同一の出力を保証できるか」で判定し、
  保証できない部分だけを探索ループに切り出す。

## 書式:GIVEN / WHEN / THEN

- 1要件 = 1見出し(**要件 = 設計上の機能の単位**)。1シナリオ = 後でテスト1メソッドに対応させる。
- **各シナリオに ID を振る**:見出しは `### S<論点番号4桁>_<連番2桁> <シナリオ名>`。ID はテスト名に
  そのまま埋め込み、spec ↔ test を機械照合する。書式・払い出し・不変性の正本は @impl-rules.md N-2
  (ここに書き写さない)。
- シナリオ名は test メソッド名に流用できる短さにする。用語は `specs/glossary.md` の語を使う(N-1)。

## 必須カバレッジ

- 正常系・異常系・境界(0件、空、上限、同時、リソース枯渇 等)を必ず網羅する。
- **「してはいけない動作」もシナリオにする。** 機能が満たすべき動作(肯定側)だけを書くと、
  実装が**余計なことをしていない**ことを誰も検証できない。異常系(不正な入力が正しくエラーに
  なる)とは別物なので、異常系を書いたから足りている、と扱わない。
  1要件につき次の3種が該当するかを**必ず確認し**、該当するものを THEN に書く。

  | 種類 | 何を否定するか | 例 |
  |---|---|---|
  | 禁止された操作・遷移 | その状況で起きてはならない振る舞い | まひ中は攻撃が合法手に**含まれない** |
  | 対象外への波及 | 効果が及んではならない範囲 | ベンチのポケモンには**付与されない** |
  | 意図しない副作用 | 変わってはならないもの(状態・引数・外部) | 再付与しても状態は**変化しない** |

  3種目は @impl-rules.md N-3 の契約(`apply_*` は純関数で引数を書き換えない等)を
  シナリオに落としたもの。契約を宣言しただけでは守られているか分からない。
- 外部効果のあるものは「発動条件」「効果」「失敗時」を分けて書く。
- 曖昧さが残る箇所は `[要確認]` を付け、人間の確定を待つ。勝手に決めない。

## 確定の流れ(人間の承認点)

全体像(どのフォルダがどう遷移するか)の図は @architecture.md「決定の流れ」。
ここは**各段で何を書き、誰が何を承認するか**を持つ。

1. `decisions/undecided/NNNN-<論点名>/topic.md` に論点を書く — 何を決めるか / 案 / 比較 /
   現在の考え / `[要確認]`。**冒頭に種別タグ(決定的 / 非決定的)を必ず書く。**
   非決定的なら `config.yaml` と `result.md` を同居させ、計測で決める(@experiment-rules.md)。
2. 議論して案を絞る。**決まるまで `undecided/` に置いたまま**にする(未決定を隠さない)。
3. **人間が決定を承認したら**、フォルダごと `decisions/decided/` へ移し、`topic.md` に
   決定 / 理由 / 却下した案 / 反映先を書く(理由は CLAUDE.md「エージェントの制約」の同項)。
4. **その場で統合する** — `specs/` に GIVEN/WHEN/THEN のシナリオを、`design/` に設計を書き起こす。
   **未統合の `decided/` を残さない。** シナリオ本文を `decided/` に重複させず、反映先だけ記す。
   設計側の書き方・承認点は @design-rules.md が正本(ここに書き写さない)。
5. 統合された `specs/` / `design/` をもとに `work/NNNN-<作業名>/` を切り、テスト・実装に進む。
   着手には @test-rules.md「着手の許可」が要る。

## topic.md テンプレ(すべての論点で共通)

決定的・非決定的、仕様・設計のどれでもこの形。**`undecided/` の間は「決定」以下を空にしておく**
(未決定を決まったように見せない)。設計の論点で特に埋めるところは @design-rules.md。

```markdown
# 論点 NNNN: <決めることの名前>

- **種別: 決定的 / 非決定的**   ← 必須。/validate が欠落を NG にする
- **状態: 未決定 / 決定済み**
- **反映先: `design/<ファイル>`**(仕様にも及ぶなら `specs/<ファイル>` も)

## 何を決めるか
<決めないと先に進めない事柄。なぜ今これを決める必要があるか>

## 案
| | 案A | 案B |
|---|---|---|
| <比較軸:依存方向 / 変更頻度 / テスト容易性 など> | | |

## 決定
<採用した案。断定形で1つに絞る。未決定の間は空>

## 理由
<なぜその案か。制約(「正」・不変条件・予算)との対応>

## 却下した案
- <案> — <なぜ採らないか>

## 決まらなかったこと(次の論点へ)
- <切り出す論点。undecided/ に別フォルダで開く>
```

## シナリオのテンプレ(`specs/` に書き起こす形)

```markdown
# 要件: <名前>
<1文で何を保証するか>

### S<論点番号>_01 <正常系の名前>
- GIVEN <前提>
- WHEN <操作>
- THEN <期待される結果>

### S<論点番号>_02 <異常系の名前>
- GIVEN ...
- WHEN ...
- THEN ...

### S<論点番号>_03 <境界の名前> [境界]
- GIVEN ...
- WHEN ...
- THEN ...

### S<論点番号>_04 <してはいけない動作の名前> [否定]
- GIVEN ...
- WHEN ...
- THEN <禁止された操作が起きない / 対象外に波及しない / 変わってはいけないものが変化しない>
```

> `[否定]` の見出しは飾りではなく、上の「必須カバレッジ」の3種を確認した形跡として残す。
> 該当が無い要件なら削除してよいが、**確認せずに消さない**。
