引数 $ARGUMENTS があればプロジェクト名として扱う(無ければ段階2で聞く)。

`DEVELOPMENT.md`「プロジェクト開始の手順」を**人間への聞き取りとして進める**。
**手順の正本は DEVELOPMENT.md 側**で、ここに書き写さない(2箇所あると片方が古いまま残る)。
この skill が持つのは「何を聞き、どこで止まり、何を確認するか」だけ。

前提確認(**欠けたら停止する。この skill の停止条件**):
- **ここがテンプレート本体でないこと。** 絶対パスと `git remote -v` を示し、「このディレクトリを
  新しいプロジェクトとして初期化してよいか」を人間に確認する。コピー直後と本体はファイル構成が
  同じで**機械判別できない**。本体で走らせると雛形と記入例が壊れる。
- **`<...>` スロットを自分で埋めないこと。** 決めるのは人間で、この skill がするのは聞き取った
  答えの**転記**まで(CLAUDE.md「エージェントの制約」)。
- **テストも実装も書かない。** baseline が要る種別でも、論点を開くところで止まる
  (@.claude/rules/test-rules.md「着手の許可」)。

## 段階1:読む・診る

1. 次の順で全て読む。**読み飛ばさない**(発足は以降の全判断の前提になる)。
   `CLAUDE.md`(特に「このリポジトリの現在の状態」)/ `DEVELOPMENT.md`「プロジェクト開始の手順」と
   「ディレクトリ構造」/ `.claude/rules/` 8本 / `gitignore.template`(追跡範囲の正本)/
   `scripts/hooks.sh` 冒頭の記入スロットと `scripts/validate.sh` 冒頭の設定 /
   `docs/glossary.md` と記入例3種(`decisions/` `docs/` `work/` の `-example-`)。
2. `/where` を実行して現在地を出す。**発足の到達度はそこでだけ判定する**(同じ判定をこの skill に
   持たない)。中断された後の再実行も、この結果を見て続きから入る。
3. 上の前提確認を人間に投げる。承認が無ければここで停止する。

## 段階2:決める・転記する

**1問ずつ聞き、答えを待つ。まとめて聞かない**(前の答えで次の質問が変わる)。聞く順は依存順 —
種別が決まると Adapt 層と「正」の性格が決まる(@.claude/rules/architecture.md「種別ごとの Adapt」)。

1. **種別**(5種から)→ 2. **プロジェクト名と1〜2文の概要** → 3. **「正」の所在** →
4. **言語/FW・環境・依存管理** → 5. **規模**(個人 / コンペ / チーム)→
6. **ドメイン語を最低1語** → 7. **OWASP の該当判定**(@.claude/rules/security-rules.md
「外部チェックリスト」。該当かつ未対策なら段階3で論点として開く)。

各回答は**差分を提示して承認を得てから書き込む**。書き込み先:

- `.claude/rules/stack.md` の `<...>`(種別・Stack・Commands・「正」・命名の記法)
- **言語を決めたら連動する5箇所を1手続きで全部埋める。** 何が5箇所かは stack.md「Stack」の
  言語/FW が正本(ここに列挙しない)。**1つでも空のまま次へ進まない** — 空のまま残ると hooks は
  NOTE を出して素通りし、「強制しているつもりで何も強制していない」状態になる。
- `.claude/rules/security-rules.md`「このプロジェクト固有」(固有事項が無ければ「無し」と**明記**する)
- `CLAUDE.md` 冒頭のプロジェクト名・概要と、**「このリポジトリの現在の状態」節の書き換え**
  (実状態に直す。**節ごと消さない** — architecture.md と validate.sh が名指しで参照している)
- `README.md` / `DEVELOPMENT.md` — **発足時点で埋まる欄だけ**。使い方・困ったときは・ライセンスなど
  動くものができてから決まる欄は空のまま残し、**引用ブロックは全部埋まるまで消さない**
  (先に消すと、後で埋める人が書き方を失う)。

続けて、**1パスずつ承認を取って**片づける(まとめて消さない。`rm -rf` は使わない):

- `gitignore.template` → `.gitignore` のリネーム。**最初のコミット前に必ず**
  (リネームするまで除外は一切効かない。@.claude/rules/security-rules.md「機密情報」)
- 記入例の削除:`decisions/*/*-example-*` `docs/*-example-*.md` `work/*-example-*` と、
  **`DEVELOPMENT.md` のディレクトリ構造ツリーの該当行**(ファイルだけ消すとツリーが古くなる)
- `docs/glossary.md` の用語行を自分のドメインの語へ置き換える(**表ごと消さない** —
  用語行が1つも無いと validate.sh が NG を出す)

最後に発火を確認する。**確認しない hooks は、効いているつもりで素通りする**:

```bash
echo '{"tool_input":{"command":"rm -rf x"}}' | scripts/hooks.sh veto   # BLOCKED と exit 2
echo '{"tool_input":{"file_path":"<整形対象の実ファイル>"}}' | scripts/hooks.sh format
```

`TEST_CMD` は**空でないことの確認まで**にする。テストの実行そのものには人間の許可が要る
(Stop フックの自動実行は人間が有効化した機械実行であって、エージェントの実行許可ではない —
@.claude/rules/test-rules.md「着手の許可」)。規模がチームなら `settings.team.json` を
`settings.json` に**追記**でマージし(`Stop` を置き換えない)、test と validate 両方の発火を見る。

## 段階3:以降を仕分ける

発足で決めなかったことを**捨てずに残す**。置き場は既存の欄だけを使い、発足メモという第4の置き場を
作らない(置き場は `docs/` / `decisions/` / コードの3つ — @.claude/rules/doc-rules.md「どこに何を書くか」)。

1. **論点 0001 を決定済みとして作る**(例 `decisions/decided/0001-project-foundation/topic.md`)。
   書式は @.claude/rules/doc-rules.md「topic.md テンプレ」。`種別: 決定的` / `状態: 決定済み` /
   `反映先: —`(要件には及ばない)。段階2で採った種別・言語・「正」と、**却下した案**を書く。
   **記入例の片づけ(段階2)を済ませてから作る** — 先に作ると記入例の番号とぶつかる。
2. **「決まらなかったこと(次の論点へ)」に以降の検討事項を列挙する。** 例:app の分け方 /
   外部との契約(入出力形式・設定項目)/ baseline / 新規依存の採用 / 時間予算・anytime 設計 /
   CI と Scale の残り / OWASP で該当したが未対策の項目。`/where` が毎回ここを読んで拾い上げる。
3. **いま開く論点だけを人間に選んでもらい**、`/new-topic` で `undecided/` に開く。採番は
   `/new-topic` に任せる(採番ロジックをこの skill に持たない)。非決定的な要素がある種別なら
   **baseline の論点を最初に開く**(@.claude/rules/experiment-rules.md「規律」)。
4. `scripts/validate.sh` を実行し、整合OK を確認して報告する。
5. **次の一手を1つだけ**示して終わる(開いた論点の議論、または `/new-topic`)。
   **決めていないことを `docs/` に先回りして書かない。**

> 発足の決定を後で覆すときは、この 0001 を書き換えない。新しい論点を開き、0001 に
> 「論点 NNNN で置き換えた」と1行だけ追記する(@.claude/rules/decision-rules.md「記録の不変性」)。
