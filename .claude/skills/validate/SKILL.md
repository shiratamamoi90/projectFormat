進行中および確定済みの仕様を検査して、欠落を報告する。

**検査は上位から順に行う**(@.claude/rules/architecture.md「整合性の優先順位」:
ドキュメント → テスト → ソースコード)。上位に違反があれば先にそれを報告し、
下位の修正はまだ提案しない(理由もその節にある)。

## 機械判定(`scripts/validate.sh`)

`scripts/validate.sh` を実行する。検査項目とその意味の正本は @.claude/rules/impl-rules.md N-8
(ここに列挙しない。2箇所に書くと片方が古くなる)。NG があれば exit 1 を返す。
どこから呼んでもリポジトリ直下を基準に動く。

- **判定はスクリプトの出力を正とする。同じ項目を目視で再判定しない。**
- 出力のセクション名がそのまま N-8 の項目名。NG 行の「ファイル:該当箇所」をそのまま報告に使う。
- 記入例の change(`changes/*-example-*`)は spec↔test 照合の対象外(実作業ではないため)。
- 機械検査できる項目を新たに見つけたら、N-8 と `scripts/validate.sh` の**両方**への追加を提案する。

## 目視判定(この skill が読んで判断する)

### 1. ドキュメント(最優先)

- 正常系だけで異常系・境界シナリオが欠けていないか。
- **肯定側だけで「してはいけない動作」のシナリオが欠けていないか** — 要件ごとに、禁止された
  操作・遷移 / 対象外への波及 / 意図しない副作用の3種を確認する
  (@.claude/rules/spec-rules.md「必須カバレッジ」。該当しないなら無くてよいが、
  **確認した形跡が無いまま肯定側だけの要件が並んでいたら指摘する**)。
- `[要確認]` タグが未解決のまま実装に進んでいないか。
- **ドキュメント同士の食い違い**(正本と写しのずれ):stack.md の Commands ↔ settings.json の
  hooks、TEMPLATE.md のディレクトリ構造 ↔ 実ファイル、CLAUDE.md の参照先 ↔ 実在するファイル。
- **設計判断が記録されているか**(@.claude/rules/design-rules.md):進行中の change の
  proposal.md に設計案(採らなかった案とその理由を含む)があるか。ADR を書く条件に該当する
  判断が、`decisions/` に残らないまま実装されていないか。
- 仕様に出てくる概念が用語集に登録されているか(未登録の語を使っていないか)。
- result.md にシードや依存固定の記述なしに数値が書かれていないか。

### 2. ドキュメント ↔ テスト

- change ごとに**総合**テスト(tests/integration/)が1本以上あるか(ID は付けない)。
- 仕様に無い挙動をテストが要求していないか(テスト側の自己解釈)。

### 3. テスト ↔ ソースコード

- テストが参照する関数・モジュールが src/ に存在するか。
- 依存方向(engine←agent←eval)を崩した import が無いか。
- N-3 の接頭辞と契約(`apply_*` は純関数、`get_*` は O(1)、`validate_*` は一覧を返す)に
  反する実装が無いか。
- テストで縛られていない分岐が実装に増えていないか。

## 報告

機械判定と目視判定を統合し、**上位の層から順に**「ファイル:該当箇所:理由」の形で列挙する。
スクリプトが exit 0 で、目視項目にも違反が無ければ「整合OK」と報告する。
